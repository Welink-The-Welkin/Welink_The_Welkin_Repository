# 换掉监测服务怎么办

本项目默认用 FeedWe 作为示例，但**代码本身不依赖任何特定服务商**。
本文说明为什么，以及换一家要做什么。

---

## 结论先说

**绝大多数情况下，一行代码都不用改。**

你只需要：把新服务商的 webhook 地址（带 `?token=`）填进去，发一条测试消息，看能不能解析出来。
如果不能，把 `data/raw/` 里那份原始 JSON 贴给我，加一个字段别名就行（通常 1 行）。

---

## 为什么能自适应

`src/parser.py` 的设计原则是"**宁可多认，也不要漏**"。解析分三层兜底：

### 第一层：已知别名表

代码里维护了几组候选字段名，覆盖常见命名习惯：

```python
_TITLE_KEYS  = ("title", "Title", "headline", "name", "subject", "article_title")
_URL_KEYS    = ("url", "Url", "URL", "link", "Link", "permalink", "href",
                "article_url", "content_url", "short_url")
_ACCOUNT_KEYS= ("account", "mp_name", "author", "source", "nickname",
                "account_name", "feed_name", "official_account", "accountName")
_TIME_KEYS   = ("publish_time", "pub_time", "published_at", "publishTime",
                "pubDate", "date", "datetime", "create_time", "timestamp",
                "publish_date", "publishDate", "sentAt")
```

所以 `{"title": "...", "link": "..."}`、`{"headline": "...", "URL": "..."}`、
`{"article_title": "...", "content_url": "..."}` 这些写法都能认。

### 第二层：递归遍历

别名表没命中时，解析器会**递归走完整棵 JSON 树**，把所有"像一篇文章"的对象收集起来。

判定标准只有两条：

1. 有一个字段值以 `http` 开头（当链接用）
2. 有一个非空字符串字段（当标题用）

所以哪怕服务商把文章藏在 `{"data": {"result": {"list": [...]}}}` 这种深层嵌套里，
或者字段名叫 `deeplink` 这种完全没见过的名字，**只要里面有 URL 和标题，就能被捞出来**。

递归有深度上限（12 层），防止畸形 payload 拖死程序。

### 第三层：纯文本兜底

如果推送的根本不是 JSON（比如纯文本摘要），会用正则抽取
`https://mp.weixin.qq.com/...` 形式的链接，用链接前面的文字当标题。

---

## 唯一硬性要求

payload 里每一篇文章必须同时具备：

| 要求 | 原因 |
|---|---|
| **标题** | 没有标题就没法做关键词匹配，也没法在弹窗里显示 |
| **链接以 `http` 开头** | 这是"这是篇文章"的判定信号；没有链接的条目会被丢弃 |

如果某家服务商的推送里**只有标题没有链接**，那它就不适配。这种情况极少见，
因为监测服务的核心价值就是给你文章链接。

## 换服务商的步骤

### 1. 在新服务商配置 webhook

地址填：

```
https://你的隧道地址/hook?token=你的token
```

隧道地址用 `python start_tunnel.py` 生成（注意它每次重启都变）。

### 2. 触发一条推送

用新服务商的「发送测试消息」功能，或者等它推真实文章。

### 3. 看原始 payload

```bash
ls data/raw/
```

最新的那个 `.json` 就是对方实际发来的内容。打开看，确认里面有没有标题和链接。

### 4. 验证解析结果

```bash
curl "http://127.0.0.1:8765/hook?token=你的token"
```

如果返回里 `parsed` 是 1（或你预期的条数），说明解析成功。
如果是 0，说明字段结构超出了别名表 + 递归兜底的范围。

**解析出 0 怎么办**：把 `data/raw/` 里那份 JSON 里的**字段名**（不用给内容值）
发到 issue 里，我加进别名表即可。这通常是一行改动。

> 注意：`data/raw/` 里的文件**包含文章的真实标题和链接**。
> 贴出来之前把标题内容替换成占位文本，只保留结构。

### 5. 确认去重正常

服务商重试或重推时不应该重复弹窗。去重是按
「`__biz` + `mid` + `idx` + `sn`」（微信长链接）或 `/s/<token>` 路径（短链接）算指纹的，
会把 `chksm`、`scene` 这类易变参数剥掉。

所以即使同一条消息被推两次、链接带了不同的追踪参数，也只会提醒一次。

## 各家服务商的形态对比

只讲形态，不讲具体价格（会变，请自行查证）：

| 形态 | 特点 | 适配难度 |
|---|---|---|
| **Webhook 推送**（本项目适用） | 有新文章时服务商主动 POST 给你 | ✅ 开箱即用 |
| **轮询 API**（需自己定时查） | 你每隔 N 分钟请求一次列表接口 | ⚠ 需要自己写定时任务，本项目没做 |
| **RSS 输出** | 服务商给一个 RSS 地址 | ⚠ 需要写 RSS 解析，本项目没做 |

本项目当前**只实现了 Webhook 接收**这一种入口。

## 如果你想加轮询或 RSS 支持

架构上是留了空间的：

- `AlertService.handle_payload(payload)` 是纯函数式入口，接受任意 dict
- 只要你能构造出 `{"articles": [{"title": ..., "url": ...}]}` 这种结构喂给它，
  后续的筛选、去重、提醒逻辑全部复用

所以加一个轮询器的做法是：

```python
# 伪代码
def poll_loop():
    while True:
        items = fetch_from_api()          # 你的取数逻辑
        payload = {"articles": items}     # 拼成已知结构
        service.handle_payload(payload)   # 复用全部后续逻辑
        time.sleep(600)
```

不需要碰 `parser.py`——直接构造标准结构反而更可靠。

> 这也是为什么 `parser.py` 写得那么宽容：**上游形态不可控，就把下游做结实。**

## 关于免费方案

微信公众号**没有**任何公开订阅接口，所有方案都得靠第三方抓取。实测过的免费路子：

| 方案 | 结论 |
|---|---|
| 搜狗微信搜索 | 搜不到小众号；按时间排序返回 0 条（反爬） |
| 自建 RSS（如 Wechat2RSS） | 需要微信登录 + 绑定微信读书，平均延迟约 6 小时，做不到"马上提醒" |

所以"免费 + 秒级"目前不存在。便宜的替代是选按公众号数量计费的服务，
而不是按查询次数计费——后者查得勤会失控。

---

## 换服务商要注意的事

1. **别把 token 明文放进第三方后台的「备注」字段**——那会被记录
2. **旧服务记得解绑**，否则两边都推，虽然去重能挡住，但白费流量
3. **新服务商的时区**：`published_at` 只是显示用，不影响匹配和去重
4. **推送频率**：如果一家服务商每条消息都要重试三次，去重库能挡住，但日志会很吵
